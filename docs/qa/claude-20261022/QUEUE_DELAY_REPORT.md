# Claude — задержка очереди перед описанием (issue #2), 22 октября 2026

База: `codex/cloud-work` `85355923702ca5117bc3ad6a8f19ce67b7446654` (source 0.137 / rules 1792609320 / History 40). Ветка `claude/notify-delay-queue`. Android не менялся: Kotlin-аналога живой очереди Telegram нет, семантика модели/цены/описаний не тронута, поэтому History и версии не повышались — нумерацию согласует Codex.

## Подтверждённые факты

1. **Механизм очереди (код).** `_verified_history` при `on_verified` проверяет **2 описания за проход**. Порядок: новые ID, затем сохранённая ротация от курсора (`normal_candidate_order`), затем стабильная сортировка `ready` первым. `ready` = карточка проходит обычный `filter_results` (лимит, 24 ч, seen) и `initial` ещё не отправлен. Больше приоритетов не было.
2. **Следствие ротации (выведено из кода, воспроизведено тестом).** В сохранённом порядке (уже после сортировки) лот внутри своего класса (ready / не-ready) поднимается ровно на 2 места за проход, только если оба проверенных лота стояли перед ним **в том же классе**. Не-ready лот при наличии ≥2 ready не двигается вообще.
3. **Доказательства 327409314879** (`docs/qa/cloud-20261021/DELIVERY_LATENCY_137.json`, read-only): места 30→28→26→24 в последовательных проходах 12:43–13:50 UTC, «следующее место» всегда 3. В 14:25 UTC при выдаче из **API** (84 карточки) лот сразу оказался в первых двух. Описание — 14:25:24.590, Telegram — 14:25:27.326.
4. **Production-логи.** Свежие runs `main` (39677267604, 39681315171) не содержат строк `Live validation queue`: журнал 0.137 на production ещё не внедрён. Ready-флаги/gate по ID в реальных runs поэтому **недоступны**.
5. **Правила уведомлений не изменены.** `filter_results`, `_notify_eligibility`, `_process_notify_candidate`, seen/дедупликация, отправка и feed не тронуты. Обычный аукцион без Best Offer по-прежнему уведомляется только в последние 24 ч.

## Вывод о причине (с явной границей)

Сдвиг ровно на 2 за проход в течение ≥4 проходов после открытия 24-часового окна, затем скачок в начало при API-карточке — это картина лота, у которого предварительный SERP-класс был **тем же, что у двух лотов перед ним**. Тут возможны два режима, оба теперь воспроизведены и исправлены:

* **A (наиболее согласуется с данными, НЕ доказан):** в HTML-карточке не было распознанных часов (`auction_time_unknown`). Лот ротировался среди не-ready — аукционов, о которых известно, что им ещё больше 24 ч. В API-карточке часы есть → `ready` → первое место. Цена 556.19 < 610 и место `de` не дают другого объяснения через лимит/страну; исходная HTML-карточка не сохранена, поэтому A — **предположение**.
* **B (доказанный дефект структуры):** лот, который **на месте** входит в 24-часовое окно (обнаружен 19.10, окно с ~12:05 21.10), получает тот же приоритет, что и ready-лоты, уже прочитанные и отклонённые. При неполных/заблокированных описаниях они остаются unseen и ready и проходят ротацию заново. Новый готовый лот ждёт до R/2 проходов.

## Исправление (ограниченное, без новых запросов)

`_live_validation_tier` + стабильная сортировка поверх сохранённой ротации (курсор и дедупликация сохранены, по-прежнему 2 описания за проход):

| Tier | Что |
|---:|---|
| 0 | ready по карточке и не читался с момента, когда стал ready |
| 1 | обычный аукцион без часов в карточке, во всём остальном ready (часы, прочитанные ранее со страницы, учитываются) |
| 2 | приоритетный лот, уже прочитанный после того, как стал ready (неполные данные/блокировка повторяются здесь) |
| 3 | остальное, в т.ч. аукционы, которым известно >24 ч |

В `ebay_access` добавлены `normal_candidate_facts` / `note_normal_candidate_facts`: по ID только `ready_at`, `checked_at`, `ends` (время окончания со страницы, только для порядка). Не хранятся цена, продавец, заголовок, описание, получатель. Хранение ограничено: 160 ID на очередь, 128 очередей, 48 ч, контекст = logic version + сигнатура фильтров + лимит. Потеря факта только повышает приоритет ID (максимум одно лишнее описание) и не может вызвать голодание. `checked_at` пишется до I/O: зависшее/заблокированное описание тоже считается попыткой.

Метрики (без персональных данных): в `Live validation queue` добавлен `tier`. Новые строки: `Live validation fairness … fresh_ready / clock_unknown / recheck / waiting / oldest_priority_wait_seconds` и `Live validation deferred … reason=fair_slice|deadline priority_deferred=N`.

## Ограничения

* Unit-тесты **не доказывают** доставку ≤15 мин после права уведомления. Нужны живые измерения после внедрения (Codex): `Live validation fairness/deferred` + feed `firstDiscoveredTime/detailsVerifiedTime/telegramConfirmedTime`.
* Режим A не доказан без исходной HTML-карточки или журнала 0.137 с production. После внедрения 0.137+ в `Live validation queue` для подобного лота должно быть видно `gate=auction_time_unknown`.
* Не исправлено (замечено, вне объёма): `normal_candidate_order` хранит множество `previous` только последней выдачи. ID из другой alias-выдачи снова считаются «новыми» и встают в начало. С tiers это влияет только на порядок внутри tier.
* Физический телефон, PC Telegram, Actions и production state не проверялись и не изменялись. Сообщение 120121 повторно не отправлялось.
