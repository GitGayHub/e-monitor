Ошибки 0.141 и исправления (обе реализации):
1. **377582903538, продан за 800 €, бот его не прислал.** «… iOS 12GB» в названии считалось неверным объёмом
   памяти. Теперь собственный объём RAM модели (12 ГБ у 17 Pro Max, 8 ГБ у 15/16) рядом с допустимым объёмом
   хранилища не считается объёмом хранилища. «iPhone 17 Pro Max 12GB» без хранилища по-прежнему отклоняется.
2. **267813864215:** «iphone 17 ProMax» (слитно) не совпадал с запросом.
3. **128150932603:** «97 % Akku OVP + Zubehörpaket» — здоровье батареи перед комплектом считалось запчастью.
4. **336857704578, 820244939746:** автоматический текст eBay пишет «Apple A17 Pro Chipsatz» для настоящего
   17 Pro Max. Если то же описание заявляет 12 ГБ RAM (такая память есть только у поколения 17 Pro), ошибочное
   название чипа больше не отклоняет лот. Без 12 ГБ RAM старое правило (178532199154) действует.
5. **407301965180, 407307707043 (мошенничество):** новое правило для всех категорий — мессенджер
   (WhatsApp/Telegram/Viber, в т.ч. «whasapp», «Whapp») рядом с номером телефона = сделка вне eBay, отказ.
   «Keine WhatsApp Anfragen» без номера не срабатывает.

Сопутствующее выравнивание: Python не считал «iPhone 15 ProMax» устройством (Kotlin считал).
Общие фикстуры `api_cases.json`/`live_cases.json` изменены в трёх ожиданиях — одинаково в обоих репозиториях:
287602029836 («16 Pro Max … Akku 88% mit Zubehörpaket») теперь проходит заголовочный этап (описание по-прежнему
обязательно), 128109766946 и 398427265231 («15 ProMax») отклоняются по цене вместо «не та модель».

## Скорость

Журналы `run_log.json` / `monitor_debug_tail.txt` main:
- проходы идут каждые ~6,5 мин; простои между заданиями Actions — около 6 % времени (не главная причина);
- 42 из 48 поисков проверяются за 15 мин, самый старый — 17 мин;
- для «Купить сейчас» от обнаружения до Telegram обычно ~0,1 мин; тысячи минут в ленте — аукционы, которые по
  правилу присылаются только в последние 24 ч;
- **377573264218 (650 €):** в 18:30 лот был виден, но цена была выше лимита; в 19:11 стал подходящим, но поиск
  оказался в конце прохода, и проверка описания отложена мягким дедлайном до 19:18.

Исправление (только сервер, `monitor.py`): свежий готовый к отправке лот (tier 0, поиск с включёнными
уведомлениями) читает описание, пока остаётся ≥30 с мягкого бюджета (резерв контрольной точки), вместо прежних
45 с; срез чтения 20 с с запасом 15 с. Жёсткий резерв воркфлоу 90 с не тронут. Механизм возобновления в
следующем проходе сохранён для переполнения (несколько готовых лотов, медленное чтение).

## Почему часть запросов «недоступна»

IP GitHub Actions получают от eBay проверку на бота (`splashui/challenge`). Бот перебирает несколько браузерных
профилей и Playwright (5–12 с на запрос), затем уходит в Browse API. По 20 последним проходам: из 453 HTML-запросов
175 вернули выдачу, 73 — настоящее «ничего не найдено», остальные ушли в API или были отложены (`search_deferred`)
из-за квоты/паузы API. HTML всё ещё работает примерно в 55 % случаев, поэтому отключать его при блокировке нельзя:
это потеряло бы находки. В статусе такие поиски честно помечены `site_error`/`blocked`, хотя карточки пришли через API.
Обход защиты eBay не делается.
